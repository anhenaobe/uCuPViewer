A. CONDICIONES DEL SISTEMA
- Dos señales analógicas independientes CH1 y CH2; al menos 64 muestras por canal en una ventana (interpretación adoptada para asegurar el mínimo exigido).
- `sample_rate_hz` significa muestras POR CANAL por segundo. Para ADC multiplexado, cada disparo provoca CH1 y CH2 secuenciales, no simultáneos; caracterizar el desfase.
- Valores inicialmente ADC RAW de 12 bits (0..4095) almacenados en uint16_t. Evitar confundir valor raw con voltaje real calibrado.
- Presets 100, 1000 y 10000 Sa/s; 40000 Sa/s se habilita solo tras demostrar estabilidad y dentro de límites de hardware.
- Una ventana mínima contiene 64 pares intercalados [CH1_0,CH2_0,CH1_1,CH2_1,...], total 128 uint16 = 256 bytes en little endian.
- Transferir una ventana completa sin que DMA sobrescriba lo leído; usar dos buffers/snapshot o pausar escritura mientras se copia al buffer TX. Definir política de nuevas capturas: preferencia reemplazar última ventana con secuencia y contador de pérdidas; NO mezclar bytes de ventanas distintas.

B. SPI ENTRE SBC Y MCU (PROPUESTA TÉCNICA)
- Raspberry Pi 4 Model B: controlador/master SPI (modelo confirmado por Andrew; configuración física y rendimiento pendientes). STM32L432KC: periférico/slave.
- Modo 0 (CPOL=0, CPHA=0), MSB-first, 8 bits, CS activo en bajo; SCLK inicial 1 MHz (NO valor máximo demostrado). Todos los GPIO 3,3 V; tierra compartida.
- Operación por solicitud del SBC (no streaming continuo obligatorio). Transacciones separadas para enviar comando, recibir estado y recibir ventana; el MCU debe preparar TX antes de que el SBC genere clocks.
- Captura terminada significa que la ventana ADC está completa y estable; transferencia SPI preparada significa que TX ya tiene la respuesta y puede atender clocks. Son condiciones distintas: la primera no garantiza la segunda. La señal READY y su relación con cada fase aún deben acordarse; no asignar nuevos bits ni respuestas sin revisión.
- Opcional RECOMENDADO: línea GPIO READY/IRQ del MCU hacia la Pi para evitar leer cuando aún no está preparado. Si no se utiliza, aplicar polling de estado con timeout e intervalos definidos por ensayo.
- Acordar medición de retardo entre transacciones y velocidad SPI estable; no presumir que 60 MHz en MCU garantizan lo mismo en Raspberry Pi.
- Comandos lógicos mínimos: PING, SET_PRESET(preset_id), START_CAPTURE, GET_STATUS, READ_WINDOW. Respuestas: OK, BUSY, BAD_CMD, BAD_CRC, NO_WINDOW y OVERRUN.
- Asociar un `sequence_id` a solicitud/respuesta; descartar paquetes con longitud/ID/CRC incorrectos y repetir si el comando es idempotente.

B1. FORMATO DE TRAMA CANDIDATO (separación de lecturas por validar con hardware)
CMD de 8 bytes: [0]=0xA5; [1]=opcode; [2]=argumento/preset; [3]=seq; [4..5]=reservado(0); [6..7]=CRC-16/CCITT-FALSE little-endian de bytes 0..5.
OPCODE: 0x01 PING; 0x02 SET_PRESET; 0x03 START_CAPTURE; 0x04 GET_STATUS; 0x05 READ_WINDOW.
Preset IDs: 0=100; 1=1000; 2=10000; 3=40000 (solo habilitar tras verificación).
ACK candidato, 8 bytes: [0]=0x5A; [1]=status; [2]=opcode eco; [3]=seq eco; [4..5]=información opcional; [6..7]=CRC16 de bytes 0..5.
READ_WINDOW: después de ACK=OK y de que el MCU prepare TX, clock de 268 bytes: [0]=0x5A, [1]=status=0, [2]=seq, [3]=preset_id, [4..5]=64 (uint16 LE), [6..7]=256 (uint16 LE), [8..263]=payload intercalado, [264..265]=CRC16 de bytes 0..263, [266..267]=padding(0). Longitud candidata conservada: 268 bytes, múltiplo de 4; no implica validación de DMA en STM32.
ADVERTENCIA: el intercambio comando/ACK/READ requiere una máquina de estados del periférico SPI y pruebas de CS, DMA y tiempos entre transacciones. Esta propuesta de bytes aún NO está comprobada; no implementarla en paralelo sin revisión técnica.

C. BACKEND LINUX ↔ FRONTEND (API HTTP / JSON PROPUESTA)

POST /api/v1/acquisition/preset con {"sample_rate_hz":1000} -> 200 {"sample_rate_hz":1000,"applied":true} al confirmar ACK real del MCU. Si falla, HTTP 503/504 o 422 con mensaje de error, nunca fingir éxito.
GET /api/v1/window/latest -> ejemplo:
{
  "window_id": 1,
  "source": "simulated",
  "sample_rate_hz": 1000,

Nota: los arrays del ejemplo ilustran estructura solamente; una respuesta real DEBE contener exactamente 64 valores en cada canal (o declarar explícitamente el N real >=64), sin puntos omitidos. E1. TIPOS / IDENTIDAD
- session_id: string UUID v4 (minúsculas, con guiones), nuevo al iniciar el proceso backend o al restablecer una sesión tras reinicio/pérdida de estado del MCU. No cambia al recargar la página. La pareja (session_id, window_id) identifica una ventana.
- window_id: entero JSON positivo e incremental por ventana adquirida/publicada en esa sesión, nunca por GET. Misma pareja implica misma ventana; puede haber saltos si se descartan capturas. No garantiza correlación exacta con el seq SPI de 8 bits.
- config_revision: entero JSON >= 0; contador de configuración dentro de la sesión. Incrementa solo al confirmar la aplicación de un preset, incluso si la frecuencia seleccionada coincide con una previa. No aumenta si la aplicación falla.
- captured_at: string ISO 8601 UTC con sufijo Z, p.ej. "2026-10-30T18:53:00.000Z". En v0.2 indica el instante en que el backend recibió/validó completamente la ventana, NO el instante físico exacto de muestreo; sincronización y timestamp del MCU quedan pendientes.
- is_stale: boolean calculado por backend al atender GET: true si edad desde captured_at supera stale_threshold_ms. No significa que la trama sea corrupta. Capturas de config_revision anterior nunca se publican como ventana actual.
- source: enum string "simulated" | "hardware" en todos los JSON de éxito que tengan cuerpo. No usar "hardware" para una confirmación del simulador.

E2. RESPUESTAS (TODOS LOS EJEMPLOS SON CANDIDATOS)
GET /api/v1/status -> 200, esquema:
{"connected":true,"capture_status":"ready","sample_rate_hz":1000,"mcu":"stm32l432kc","source":"simulated","session_id":"c8248e7a-6282-439f-a087-e7c0f6a74244","config_revision":0}
connected significa que el proveedor ACTIVO (simulador o MCU) responde; connected=true con source=simulated NO acredita enlace con el MCU. En modo simulado, mcu se refiere al dispositivo objetivo (no conectado); el frontend debe mostrar SIMULATED.
capture_status enum: idle, configuring, capturing, ready, error, unavailable.
idle: proveedor listo sin adquisición activa; configuring: SET_PRESET en curso; capturing: adquisición en curso; ready: ventana válida en revisión actual; error: fallo de adquisición/protocolo; unavailable: proveedor no accesible.
Durante configuración: GET /status -> 200, capture_status=configuring, con sample_rate_hz y config_revision de la última configuración confirmada. connected se calcula del proveedor activo; un fallo de captura no implica necesariamente desconexión.

POST /api/v1/acquisition/preset request {"sample_rate_hz":1000} -> 200 solo después de confirmar aplicación en el proveedor:
{"sample_rate_hz":1000,"applied":true,"source":"simulated","session_id":"c8248e7a-6282-439f-a087-e7c0f6a74244","config_revision":1}
En source=simulated, applied=true significa aplicado exclusivamente al simulador. En source=hardware significa SET_PRESET confirmado por el MCU conforme al ACK y semántica que se valide; NO garantiza que haya llegado una ventana nueva. Para una operación de preset concurrente o incompatible con captura en curso, responder 409; serializar el acceso a SPI. Si una captura previa ya estaba siendo transferida, descartarla al confirmar nueva configuración. Las solicitudes GET en curso pueden devolver la ventana previa: frontend debe verificar config_revision antes de representarla. Si POST falla, conservar revisión y preset confirmados; no retornar applied=true.

GET /api/v1/window/latest -> 200 si existe ventana completa VALIDADA en revisión actual; ejemplo esquemático:
{"session_id":"c8248e7a-6282-439f-a087-e7c0f6a74244","window_id":25,"config_revision":1,"captured_at":"2026-10-30T18:53:00.000Z","is_stale":false,"source":"simulated","sample_rate_hz":1000,"samples_per_channel":64,"adc_resolution_bits":12,"unit":"adc_counts","channels":{"ch1":[0,1],"ch2":[3,4]}}
Los arrays son ESQUEMATICOS; respuesta operativa debe contener exactamente N enteros ADC [0..4095] por canal, N>=64, misma longitud. Las muestras corresponden a la revision vigente y a una sola captura, y sample_rate_hz es POR CANAL. window_id se mantiene si se solicita repetidamente la misma ventana.
GET /window/latest -> 204 SIN CUERPO cuando proveedor activo accesible pero no hay ventana válida (inicio, captura todavía pendiente, o periodo de invalidación tras cambio). Si el proveedor no está disponible -> 503; si una operación que requiere respuesta del MCU excede el timeout -> 504; NO enmascarar fallos como 204.
Política de ventanas: al CONFIRMAR cambio de preset, invalidar cache de la revisión anterior. No publicar una ventana nueva hasta asociarla de forma verificable a la nueva revisión. La verificación MCU/SPI para garantizar la asociación aún NO está diseñada/validada; no inferirla solo de sample_rate_hz.
Frescura y sincronización: is_stale=true puede coexistir con HTTP 200; el frontend debe etiquetar ventana antigua y evitar llamarla captura en vivo. El frontend consulta cada ~2 s; evitar solicitudes solapadas.

E3. ERRORES
Para error HTTP con cuerpo: {"error":{"code":"ACQUISITION_BUSY","message":"Adquisicion ocupada","details":null}}
error.code es string de enum; message es string legible; details es null u objeto JSON (nunca string/array/stacktrace).
409 ACQUISITION_BUSY: conflicto de operación; opcional details.operation string.
422 INVALID_PRESET: frecuencia no admitida/no habilitada; opcional details.requested_sample_rate_hz integer y details.allowed_sample_rates_hz array de enteros.
503 MCU_UNAVAILABLE: proveedor hardware inaccesible; si falla el proveedor simulado se puede usar PROVIDER_UNAVAILABLE (503), sin atribuirlo falsamente al MCU.
504 MCU_TIMEOUT: timeout de una operación hardware; para simulado se puede usar PROVIDER_TIMEOUT (504) si aplica.
Errores 500 internos inesperados: INTERNAL_ERROR, sin incluir rastros internos en la respuesta.
En errores de validación del cuerpo POST, mapear al esquema JSON uniforme y responder 422 INVALID_PRESET si corresponde.
Headers: Content-Type application/json para cuerpos JSON; 204 no lleva cuerpo.
